# План

Каждый этап заканчивается работающим состоянием: тесты зелёные, README описывает, что уже можно сделать.

## Этап 0. Дизайн — готово
- Архитектура, домен, машина состояний, сага, список гонок (`docs/architecture.md`).
- Каталог из двух роботов (`bots`), dev-окружение (`infra`).

## Этап 1. Каркас и назначения

Сделано: каркас, конфиг, логи с маскированием, health, метрики, миграции, интеграционные тесты, шифрование
секретов, адаптер Dokploy (проверен на живом v0.31.4), назначения, вход операторов, аудит. Роли Postgres и ротация
мастер-ключа перенесены на этап 2.

- NestJS-приложение, конфиг через zod, pino, health, `/metrics`.
- Kysely, первые миграции: `destination`, `audit_event`.
- Шифрование секретов (envelope, AES-256-GCM) с тестами.
- Адаптер Dokploy: `project.all`, `environment` (проверка ключа при добавлении), retry с jitter,
  circuit breaker и таймаут на каждое назначение.
- CRUD назначений в админ-API, вход оператора (сессия в cookie).
- CI: lint, typecheck, unit и интеграционные тесты (сервисы Postgres и RabbitMQ в CI).

## Этап 2. Клиенты, шаблоны, сага

Сделано (шаг 1): каталог роботов с неизменными версиями шаблонов (`bun run catalog:sync`), клиенты с токеном,
привязанным к режиму, и подтверждаемым переходом в боевой режим вместе со счётом.

Сделано (шаг 2): развёртывания, операции, outbox и RabbitMQ.
- Шаблоны Handlebars компилируются и сверяются с переменными при синхронизации каталога; адрес T-Invest
  шаблон берёт из `platform.tinvestAddress`, а не из конфига оператора; `default` из схемы подставляются.
- Развёртывания и операции с `Idempotency-Key`; новое — только на действующем шаблоне, активном клиенте и
  включённом назначении, в той же транзакции; режим торговли закреплён на развёртывании.
- Запрет архивации и смены режима клиента с роботами; на выключенном назначении — только stop и delete.
- Relay outbox → RabbitMQ (`PROCESS_ROLE=relay`): `mandatory`, таймаут подтверждений, выход при потере брокера.

Сделано (шаг 3a): воркер саги поверх Dokploy (`PROCESS_ROLE=worker`).
- Шаги provision, redeploy, start, stop, delete; аренда шага, одноразовые отложенные команды, опрос деплоя через
  outbox (`available_at`); формы ответов Dokploy сверены с живым v0.31.4, сквозной прогон BITA в песочнице.
- Рендер конфига с экранированием под env и TOML, адреса T-Invest по `tradingMode`, корень сертификатов T-Invest
  роботу; робот без проверки TLS — только песочница.

Шаг 3b — проверка токена и счёта клиента через T-Invest API (при сохранении токена и переходе в боевой режим),
заодно проверить, отвечает ли боевой хост на методы песочницы (BITA).

Шаг 3c — reconciler: операции, у которых пропала команда (аренда истекла, сообщения нет), — переотправить или
закрыть; очистка `idempotency_record` и опубликованных `outbox_message` по возрасту (индексы уже есть).

Остальное этапа:
- операция «ротация токена → redeploy всех роботов клиента»;
- форк contest-2022 с проверкой сертификата; `upstream.ref` роботов — закрепить на SHA;
- метрика или алерт на порцию outbox, которую брокер возвращает (сейчас — только error-лог раз в 2 с).

- Перенесено с этапа 1. Ротация мастер-ключа: прежний ключ в конфиге, фоновая перешифровка, контрольный конверт на старте
  (падать, если текущий ключ не открывает секреты).
- Роли Postgres: миграции — владелец схемы, приложение — роль без владения и без UPDATE/DELETE/TRUNCATE на
  `audit_event`. Пока приложение ходит владельцем и технически может отключить триггер аудита.
- Общий ограничитель входов (Redis) вместо счётчика в памяти реплики; чистка истёкших сессий; «выйти везде».
- Тесты гонок воркера: повторная доставка шага, вебхук против опроса, delete против идущего деплоя.

## Этап 3. Обратная связь от Dokploy
- Вебхук `notification.createCustom` с подписью-секретом в заголовке, inbox с дедупликацией.
- Reconciler: дрейф развёртываний относительно Dokploy.
- Логи: `application.readLogs` → SSE, раздача между репликами через Redis pub/sub.

## Этап 4. Админка
