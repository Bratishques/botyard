# Botyard — архитектура

Botyard разворачивает торговых роботов T-Invest API (Т-Банк Инвестиции) для клиентов на серверах под
управлением [Dokploy](https://dokploy.com). Оператор в админке заводит назначения (Dokploy-инстансы),
клиентов с их токенами T-Invest и выбирает шаблон робота. Остальное делает платформа: создаёт приложение
в Dokploy, собирает образ из исходников робота, передаёт конфиг и секреты, запускает, следит
за состоянием и отдаёт логи.

Роботы — сторонние open-source проекты (см. репозиторий `bots`). Платформа их не меняет: она
оркестрирует развёртывание. По умолчанию роботы работают только в **песочнице** T-Invest.

## Компоненты

```
 ┌────────────┐  HTTPS   ┌──────────────────────── api (NestJS) ─────────────────────────┐
 │ admin (SPA)│ ───────► │ HTTP: админ-API, вебхуки Dokploy, SSE логов                   │
 └────────────┘          │                                                               │
                         │ Postgres ◄── сценарии пишут состояние + outbox одной транзакцией│
                         │    │                                                          │
                         │    └─► outbox relay ──► RabbitMQ ──► worker (шаги саги)       │
                         │                                         │                     │
                         │ reconciler (по расписанию): сверка с Dokploy, зависшие саги    │
                         └─────────────────────────────────────────┼─────────────────────┘
                                                                   │ x-api-key, у каждого назначения свой
                                   ┌───────────────────────────────▼──────────────┐
                                   │ Dokploy (назначение)                         │
                                   │  git clone робота → docker build → Swarm     │
                                   │  контейнер робота ──gRPC──► T-Invest API     │
                                   └──────────────────────────────────────────────┘
```

- **api** — один кодовый репозиторий, несколько процессов: `http`, `worker`, `relay`, `reconciler`. Каждый
  процесс stateless, реплик может быть несколько.
- **Postgres** — источник истины: назначения, клиенты, развёртывания, журнал операций, outbox, inbox
  вебхуков, аудит.
- **RabbitMQ** — доставка команд саги воркерам. Доставка «хотя бы один раз», поэтому каждый шаг идемпотентен.
- **Dokploy** — исполнитель. Его API не идемпотентен и не типизирован в ответах (OpenAPI описывает только
  запросы), поэтому весь доступ идёт через один адаптер с контрактными тестами.

## Домен

| Сущность | Смысл | Ключевые поля |
|---|---|---|
| `Destination` | Куда разворачивать: Dokploy-инстанс и, по желанию, удалённый сервер в нём | `baseUrl` (нормализован), `apiKey` (зашифрован, наружу — `apiKeyHint`), `projectId`, `environmentId`, `serverId?`, `status`: `ACTIVE` / `UNREACHABLE` (последняя проверка не прошла) / `DISABLED` (выключено оператором, новые развёртывания не принимает), `version` |
| `Customer` | Для кого разворачивается робот | `name`, `accountId`, `tinvestToken` (конверт привязан к режиму: токен песочницы не открывается как боевой), `sandbox` (по умолчанию `true`; боевой режим — новый токен и подтверждение именем), `status` (`ACTIVE` / `ARCHIVED`), `version` |
| `BotTemplate` | Описание робота из репозитория `bots` (`bun run catalog:sync`) | `gitUrl`, `ref`, `dockerfile`, `context`, `configSchema`, способ передачи конфига (`env` / `file`); текущая версия и отметка «выведен» |
| `BotTemplateVersion` | Неизменная версия шаблона; на неё ссылается развёртывание | `version` — SHA-256 канонического манифеста и файлов, `manifest`, `files`; UPDATE и DELETE запрещены триггером |
| `BotDeployment` | Робот конкретного клиента на конкретном назначении из конкретной версии шаблона | `status`, `config` (с подставленными умолчаниями схемы), `tradingMode` (режим клиента при создании), `dokployAppId?`, `appName` (детерминирован), `activeOperationId?` (только своя операция — составной FK) |
| `Operation` | Одна операция над развёртыванием: provision, start, stop, redeploy, delete | `kind`, `status`, `step`, `attempt`, `error?`, `requestedBy` |
| `OutboxMessage` | Команда или событие, записанное в одной транзакции с состоянием | `topic`, `payload`, `publishedAt?` |
| `IdempotencyRecord` | Ответ на запрос с `Idempotency-Key` | `scope` (оператор и действие), `key`, `requestHash`, `statusCode`, `response` |
| `InboxMessage` (этап 3) | Принятый вебхук Dokploy, дедупликация | `dedupKey` (уникален), `receivedAt` |
| `Operator` | Оператор админки | `email` (уникальна, в нижнем регистре), хеш пароля argon2id |
| `OperatorSession` | Сессия входа | SHA-256 токена (сам токен — только в cookie), `expiresAt`, `revokedAt` |
| `AuditEvent` | Кто, что и когда сделал в админке. Только дописывание: UPDATE, DELETE и TRUNCATE запрещены триггером | `actor`, `action`, `targetType`, `targetId`, `payload` (объект), `createdAt` (ставит база) |

`appName` в Dokploy выводится из id развёртывания (`by-<последние 12 hex-символов id>`: начало UUIDv7 — время). Это естественный ключ
идемпотентности для API, у которого своего ключа нет (см. сагу).

## Машина состояний развёртывания

```
  create (provision)          deploy ok
 ─────────────────► PROVISIONING ───────────► RUNNING ◄──────┐
                          │                       │  stop      │ start
                          │ ошибка                ▼            │
                          ▼                   STOPPED ─────────┘
                        FAILED ── redeploy ──► RUNNING / FAILED
   любое, кроме DELETED ── delete ──► DELETING ──► DELETED (терминально)
```

Черновика нет: развёртывание создаётся сразу с операцией `PROVISION`. Допустимые статусы операций —
`OPERATION_RULES` в `src/modules/deployments/domain/deployment.ts`: start — из `STOPPED`, stop — из `RUNNING`
и `FAILED` (упавший запуск мог оставить робота перезапускаться в цикле),
redeploy — из `RUNNING`/`STOPPED`/`FAILED`, delete — из любого, кроме `DELETED` (из `DELETING` — повтор упавшего
удаления). На выключенном назначении запуск и передеплой запрещены, остановка и удаление — нет.

- Переход — только условный `UPDATE ... WHERE id = $1 AND status = $from`. Проигравший получает 0 строк
  и ничего не делает.
- В каждый момент у развёртывания не больше одной активной операции: её захватывает условная запись
  `activeOperationId IS NULL` вместе с проверкой допустимого статуса. Вторая команда, в том числе `delete`,
  получает `409 OPERATION_IN_PROGRESS` — оператор повторяет её после завершения текущей (очередь операций
  усложнила бы отмену и не нужна при одном операторе на развёртывание).
- Запрос оператора только записывает: развёртывание, операцию и команду в outbox — одной транзакцией. Ответ —
  принятая операция; работу с Dokploy делает воркер, транзакция не держится на сетевом вызове.
- `Idempotency-Key`: запись ключа, работа и сохранение ответа — одна транзакция (работа — только запись в базу).
  Повтор в полёте ждёт на уникальном ключе и получает ответ первого; ошибка откатывает и ключ, поэтому повтор
  после ошибки выполняется заново. Scope — оператор и действие; все операции над одним развёртыванием делят
  scope, и тот же ключ для stop и start — `409 IDEMPOTENCY_CONFLICT`. Записи пока не чистятся (roadmap).
- **Режим торговли закреплён на развёртывании** (`tradingMode`). Переключить клиента между песочницей и боевым
  нельзя, пока у него есть неудалённые развёртывания (`409 CUSTOMER_HAS_DEPLOYMENTS`), — иначе песочный робот
  при следующем redeploy получил бы боевой токен. Боевой робот создаётся только явно, у боевого клиента.
- **Зависшая операция.** Воркер, упавший посреди шага, не теряет его: сообщение не подтверждено, RabbitMQ отдаст
  его снова, а дубль во время аренды откладывается до её конца (см. «Сага»). Остаётся случай, когда пропала
  сама команда (outbox удалили руками, очередь очищена): развёртывание держит `activeOperationId`, и новые
  операции получают 409. Это снимет reconciler (шаг 3c); до него — руками в базе.
- **Робот без проверки TLS** (`security.verifiesTls: false` в манифесте) создаётся только у клиента в песочнице:
  `422 DEPLOYMENT_TEMPLATE_NOT_LIVE_SAFE`. Такой робот отдал бы боевой токен любому, кто встал посередине.

## Сага операций

Оркестрация: шаги задаёт `SAGA` (`src/modules/deployments/domain/saga.ts`), воркер (`PROCESS_ROLE=worker`,
`OperationWorker`) выполняет по одному шагу на сообщение `operation.step`. Provision и redeploy идут одним
путём — конфиг и токен перерисовываются, приложение находится по `appName`.

| Шаг | Вызов Dokploy | Как сделан повторяемым |
|---|---|---|
| `ensure_app` | `application.search` → `application.create` | Сначала поиск: если ответ на прошлый `create` потерялся, приложение найдётся, а не создастся второе. Два найденных — отказ, угадывать нельзя |
| `configure` | `saveGitProvider`, `saveBuildType`, `saveEnvironment`, `mounts.create/update/remove` | Перезапись; файлы сверяются по `mountPath`, лишний (шаблон сменил путь) удаляется вместе со старым токеном |
| `prepare_deploy` | `deployment.all` | Запоминает последний деплой до запуска |
| `deploy` | `application.deploy` | Если после запомненного уже есть новый деплой — прошлая попытка его запустила, второй не нужен |
| `await_deploy` | `deployment.all` | Опрос раз в 10 с через outbox: `done` — RUNNING, `error` — FAILED, дольше 30 мин — FAILED |
| `start` / `stop` | `application.start` / `application.stop` | Идемпотентны в Dokploy |
| `delete` | `application.search` + `application.delete` | Удаляются все приложения по `appName` и по сохранённому id; «уже удалено» — только 404 «Service not found» (404 бывает и у Traefik перед перезапускающимся Dokploy); DELETED — только если поиск после удаления пуст |

**Особенности Dokploy v0.31.4, проверенные на живом инстансе** (test/fixtures/dokploy/README.md):
- `application.create` дописывает к `appName` случайный хвост (`by-…` → `by-…-gz6yu7`), а `application.search`
  ищет подстрокой. Поэтому совпадение проверяет адаптер: то же окружение и `<appName>` или `<appName>-<хвост>`;
- `application.deploy` только ставит деплой в очередь, исход — в `deployment.all`;
- `application.start` выполняет `docker service scale` и ждёт, пока сервис сойдётся: у робота, падающего при
  запуске, — никогда. Вызов ограничен 30 с, попыток две, затем операция FAILED с подсказкой смотреть логи;
- ответы `application.one`, `stop`, `mounts.*` содержат env и файлы робота вместе с токеном — схемы адаптера
  выбирают только нужные поля, сырой ответ не логируется.

**Протокол воркера:**

```
  аренда шага: UPDATE operation SET attempt+1, lease_until WHERE step = $step AND аренды нет
               AND context.wakeNonce = $wake                     ← иначе сообщение устарело или занято
  ─ вне транзакции: сверка основания и вызовы Dokploy ─
  транзакция:  { переход к следующему шагу + команда в outbox }        WHERE step, attempt совпадают
           или { отпустить аренду, новая wakeNonce + отложенная команда в outbox (available_at) }
           или { итог операции + статус развёртывания, снять activeOperationId }
```

- **Повторная доставка — штатно.** Дубль во время аренды Dokploy не трогает, а откладывается до конца аренды
  (если держатель аренды упал, шаг подхватит эта отложенная команда). Устаревшая команда — шаг уже другой,
  операция завершена — отбрасывается.
- **Отложенная команда одноразова.** Повтор и опрос публикуются через outbox с `available_at` и меткой
  `wakeNonce`; захват требует совпадения метки, поэтому дубль, пришедший после паузы, не запустит вторую
  цепочку опросов.
- **Аренда, а не блокировка.** Строка операции не держится под транзакцией на время вызова Dokploy. Воркер, у
  которого аренду перехватили, ничего не запишет: все его записи — по шагу и `lease_id` (номер попытки не годится:
  ожидание его сбрасывает, и номер повторяется). Аренда — 5 мин, худший шаг по таймаутам клиента — около 100 с.
  Захват и проверка причины отказа — два запроса; если между ними аренда истекла, захват повторяется, а не
  отбрасывает единственную команду.
- **Основание перечитывается перед каждым шагом:** операция всё ещё активна у развёртывания; назначение не
  выключено — на шагах до запуска деплоя и на start (запуск, принятый до выключения, здесь и отказывает). После
  `deploy` выключение уже не останавливает операцию: деплой идёт в Dokploy, и FAILED соврал бы. Клиент (не в архиве,
  режим совпадает с `tradingMode`) сверяется на `configure` — там, где открывается его токен. Ключ Dokploy и токен
  открываются на время шага; текст ошибки перед записью в операцию и аудит очищается от них и маскируется.
- **Неизвестный исход ≠ отказ.** Сеть, таймаут, 5xx, 429 — повтор шага с экспонентой и полным jitter (до 6
  попыток, не раньше `Retry-After`). 401/403, прочие 4xx, непонятный ответ, ошибка рендера — отказ операции.
  Созданное в Dokploy при отказе не удаляется: оператор видит логи упавшей сборки, убирает — операция `delete`.
- **Итог:** provision, redeploy, start → RUNNING или FAILED; stop → STOPPED или FAILED; delete → DELETED, а при
  отказе развёртывание остаётся DELETING и удаление можно повторить. Итог — в аудите (`deployment.<kind>_succeeded`
  или `_failed`, actor `system:worker`).

**Конфиг робота** (`HandlebarsConfigRenderer`). Шаблоны проверены при синхронизации каталога; при рендере —
`strict` (отсутствующее поле — ошибка) и экранирование под формат: значения env — только по белому списку
символов (Dokploy разбирает env как dotenv, где перевод строки, `#` и `$` меняют смысл); строки TOML —
escape-последовательности, результат разбирается `Bun.TOML.parse`. Адрес T-Invest — `TINVEST_ADDRESS[tradingMode]`.

**Корень сертификатов T-Invest.** Хосты T-Invest подписаны Russian Trusted Root CA Минцифры, которого нет в
стандартных хранилищах. Проверено 2026-11-24: Go в `alpine:3.11` (рантайм BITA) и `golang:1.18-alpine` (рантайм
contest-2022) без него получает `x509: certificate signed by unknown authority`. Платформа кладёт каждому роботу
корень file mount'ом (`/etc/ssl/botyard/tinvest-root-ca.pem`, отпечаток закреплён тестом) и `SSL_CERT_FILE` на него:
робот проверяет сертификат T-Invest. `SSL_CERT_FILE` заменяет только файл корней по умолчанию: каталоги
сертификатов (`/etc/ssl/certs`, `SSL_CERT_DIR`) Go читает по-прежнему. Имена платформы шаблон занять не может.

## Outbox и relay

Сценарий пишет команду в `outbox_message` той же транзакцией, что и состояние. Процесс `PROCESS_ROLE=relay` берёт
порцию неопубликованного под `FOR UPDATE SKIP LOCKED`, публикует в RabbitMQ (обменник `botyard`, очередь
`botyard.operation.step`, `persistent`, `messageId` = id сообщения outbox) с подтверждением брокера и отмечает
`published_at` — всё в одной транзакции. Брокер недоступен — откат, сообщение уйдёт позже. Брокер подтвердил, а
коммит не прошёл — сообщение уйдёт повторно с тем же `messageId`: отдельного inbox нет, воркер сверяет шаг
операции и метку пробуждения условной записью, и повтор уже сделанного шага отбрасывается.

- `available_at`: relay публикует только наступившие сообщения — так воркер откладывает повтор и опрос.

- Публикация `mandatory`: сообщение, которому нет очереди, брокер возвращает, и порция откатывается, а не
  отмечается опубликованной. У каждой темы outbox обязана быть привязка — это проверяют типы (`BINDINGS`).
- Подтверждение ждём не дольше 10 с; на пуле relay стоит `idle_in_transaction_session_timeout`, чтобы
  зависший канал не держал строки outbox заблокированными.
- Потеря соединения или канала — relay завершается с кодом 1, перезапускает оркестратор. Своего
  переподключения нет. Логи relay — тот же JSON pino с маскировкой, что у http.
- Опубликованные строки пока не удаляются (roadmap).

## Reconciler

По расписанию, по каждому назначению:
- операции, которые висят на шаге дольше порога, переотправляются в очередь;
- развёртывания `RUNNING` сверяются с `application.one`. Если приложение остановили или удалили руками
  в Dokploy, это фиксируется как дрейф и показывается в админке, а не «чинится» молча;
- операции, застрявшие без движения (см. «Зависшая операция»), закрываются как `FAILED`, чтобы снять захват.

## Гонки, которые разбираются явно

| Сценарий | Защита |
|---|---|
| Двойной клик «Развернуть» | `Idempotency-Key` от админки, `PRIMARY KEY (scope, key)` в `idempotency_record` в той же транзакции; повтор возвращает тот же ответ |
| «Стоп» во время провижининга | Захват `activeOperationId` условной записью; вторая операция получает 409 |
| Создание против архивации клиента, смены режима, выключения назначения | Создание держит клиента, назначение и шаблон под `FOR SHARE`; архивация и смена режима — клиента под `FOR UPDATE` с проверкой живых развёртываний |
| Запуск против выключения назначения | После захвата операции назначение читается под `FOR SHARE`; выключено — откат захвата |
| Синхронизация каталога во время создания | Шаблон блокируется отдельным запросом, манифест читается следующим — со свежим снимком |
| Вебхук и опрос пришли одновременно | Условный переход `WHERE status = $from`; проигравший — no-op |
| RabbitMQ доставил шаг дважды | Аренда шага условной записью до вызова Dokploy; дубль во время аренды откладывается, после — устарел |
| Дубль отложенной команды (опрос, повтор) | Метка `wakeNonce`: команда одноразова |
| Воркер завис дольше аренды, шаг взял другой | Записи по шагу и номеру попытки: опоздавший ничего не запишет |
| Потерян ответ на `application.create` | Поиск по `appName` перед созданием |
| Потерян ответ на `application.deploy` | Сравнение последнего деплоя с запомненным до запуска |
| Назначение выключили, режим клиента сменили в обход сценария, операцию сняли руками | Основание перечитывается перед каждым шагом |
| Назначение переехало (адрес, окружение, сервер), пока на нём роботы | Запрещено (`409 DESTINATION_HAS_DEPLOYMENTS`) под блокировкой назначения: сага ищет роботов по прежнему адресу |
| Ключ назначения заменили ключом другого пользователя Dokploy | Новый ключ должен видеть приложения роботов (`422 DESTINATION_KEY_CANNOT_SEE_DEPLOYMENTS`); проверка повторяется под блокировкой |
| Ротация API-ключа назначения во время операции | Ключ читается на каждом шаге, а не кешируется на всю сагу |
| Ротация токена клиента | Новый токен → операция `redeploy` у всех его развёртываний; старый токен из env Dokploy перезаписывается |
| `delete` против идущего деплоя | `delete` ждёт завершения активной операции (409 до её конца) |

Пункты покрыты интеграционными тестами с принудительным переплетением (`test/integration/deployments.test.ts`,
`worker.test.ts`). Ротация ключа назначения покрыта тем, что ключ открывается на каждом шаге; операции
«ротация токена → redeploy всех роботов клиента» пока нет (roadmap).

## Безопасность

- Токены T-Invest и API-ключи Dokploy хранятся с envelope encryption (`src/shared/crypto`): AES-256-GCM,
  свой ключ данных на каждую запись, мастер-ключ из окружения за портом `KeyEncryptionKey`. Заголовок
  конверта (версия, номер ключа) входит в AAD обоих слоёв.
- **Контекст секрета** (`secretContext`) — сущность, id, поле и то, куда секрет уходит: для ключа Dokploy —
  нормализованный `base_url`. Конверт, переложенный в другую строку, не откроется, а подмена `base_url`
  в базе не отправит ключ на чужой хост. Поэтому смена адреса назначения требует ввести ключ заново.
- **Модель угроз:** дамп базы или запись в неё, утечка логов. Доступ к процессу или окружению (там мастер-ключ)
  шифрованием не закрывается. Обнуление ключей в памяти — по возможности, не гарантия.
- **Ротация мастер-ключа не реализована.** `SecretBox` умеет читать старые конверты прежним ключом, но конфиг
  передаёт один ключ и перешифровки нет. Ловушка: сменить `SECRETS_MASTER_KEY`, не сменив
  `SECRETS_MASTER_KEY_ID`, — и все секреты перестанут открываться с общей ошибкой.
- **Вход операторов.** Пароль — argon2id; сессия — случайный токен 256 бит в cookie (HttpOnly, SameSite=Strict,
  Secure), в базе — только его SHA-256. Сессия проверяется по базе на каждом запросе: отзыв действует сразу.
  - Перебор паролей: попытка резервируется до хеширования одним синхронным шагом — залп параллельных
    запросов не обгоняет лимит. Лимит — 5 неудач на почту и 20 на IP за 15 мин, `429` с `Retry-After`;
    удачный вход снимает свой резерв. Неизвестная почта неотличима по ответу (хеш-приманка).
  - IP клиента за прокси: `TRUST_PROXY` — число прокси (за Traefik Dokploy — 1) или подсети; `true` запрещён,
    иначе `X-Forwarded-For` подделывается и лимит по IP обходится. Без настройки за прокси у всех клиентов
    один адрес, и аноним мог бы запереть вход всем.
  - Нагрузка: не больше 4 одновременных проверок argon2, очередь ограничена, сверх неё — `503 LOGIN_BUSY`.
  - Аудит: неудачи пишутся только для существующих операторов; остальные — метрикой
    `botyard_login_failures_total`, чтобы аноним не раздувал неудаляемый журнал.
  - CSRF: SameSite=Strict и только JSON у изменяющих запросов, CORS закрыт.
  - Принятые риски: лимит входов — на реплику (общий счётчик — этап 2); запрос, прошедший проверку сессии
    до выхода, доделывается; истёкшие сессии пока не чистятся; у существующей почты неудача на одну запись
    аудита дольше (~1 мс на фоне argon2) — оракул существования, который лимиты делают дорогим; успешный вход
    владельца обнуляет неудачи его почты — у атакующего снова 5 попыток; лимит по IP обходится сменой адреса
    внутри IPv6 /64.
- **Боевой режим клиента.** Защищает: подмена флага `sandbox` записью в базу в обход сценария — конверт токена
  привязан к режиму и не откроется (отказ безопасный); переход и смена счёта боевого клиента — только с
  подтверждением именем; в аудите отдельные события (`customer.live_enabled`, `customer.sandbox_enabled`,
  `customer.account_changed`) с прежним и новым счётом. Не защищает (принятые риски и план):
  - повтор старого конверта того же клиента и режима из бэкапа: в контексте нет версии;
  - куда уходит токен: адрес API T-Invest в конфиге робота оператор не задаёт — шаблон берёт его из
    `platform.tinvestAddress`, воркер подставляет `TINVEST_ADDRESS[tradingMode]` (адреса — из официальной
    документации T-Invest, `src/shared/tinvest/tinvest.ts`). Исключение — BITA: адрес зашит в код робота (см.
    «Открытые вопросы»). Сертификат T-Invest робот проверяет корнем, который даёт платформа; робот, который не
    проверяет его вовсе (`verifiesTls: false`), — только песочница;
  - Dokploy хранит env и файлы робота с токеном у себя: env в v0.31.4 по исходникам — шифрованным, содержимое
    file mount — открытым текстом (известный компромисс ниже);
  - подмена версии шаблона (чужой `gitUrl`) прямой вставкой в базу: триггер запрещает правку, но не вставку.
    Атакующий с записью в базу уже управляет назначениями и развёртываниями — подпись версий (HMAC от
    мастер-ключа) отложена;
  - подтверждение именем — защита от случайного клика, а не второй фактор при захваченной сессии;
  - что «боевой» токен действительно боевой и счёт принадлежит токену — проверка через T-Invest API (шаг 3b).
- **Каталог роботов** — недоверенный ввод из публичного репозитория: симлинки отклоняются, манифесты и
  схемы конфига проверяются строго, синхронизации идут по одной под блокировкой и полностью попадают в аудит.
- **Предпросмотр назначения** ходит по адресу, который ввёл оператор, — внутреннюю сеть может опросить
  только вошедший оператор, `http` выключен по умолчанию, а текст ответа чужого адресата в API не уходит
  дальше кода ошибки и статуса.
- Логи маскируют секреты по имени поля и виду значения на любой глубине. Секреты не кладутся в путь URL
  (вебхук Dokploy подписывается заголовком), query в лог не пишется.
- **Известный компромисс:** Dokploy хранит переменные окружения и содержимое file mount у себя открытым
  текстом. Назначение должно быть доверенным, это написано в README и в форме добавления назначения.
- Песочница по умолчанию. Боевой режим (`sandbox = false`) — отдельный флаг клиента, его включение
  требует подтверждения и пишется в аудит.
- API-ключ Dokploy даёт полный доступ к инстансу, поэтому у каждого назначения он свой, и проверка
  ключа (`project.all`) делается при добавлении.

## Открытые вопросы

- Ответы Dokploy в OpenAPI не описаны: схемы ответов фиксируются на живом инстансе в контрактных тестах.
- Роботы в `bots` написаны в 2022 году (Go 1.18). BITA собирается и запускается в Dokploy v0.31.4 (проверено
  2026-11-24 сквозным прогоном воркера); contest-2022 пока только рендерится, сборка не проверялась.
- Адрес API у BITA захардкожен (`invest-public-api.tinkoff.ru:443`). На 2026-11-24 домен резолвится,
  но если его отключат, BITA потребует форк. Это исключение из правила «адрес даёт платформа»: режим BITA
  выбирается только токеном, а песочница по документации T-Invest — отдельный хост. Отвечает ли боевой хост
  на методы песочницы, без настоящего токена песочницы не проверить — проверка вместе с шагом 3b.
- contest-2022 не проверяет сертификат T-Invest (`InsecureSkipVerify`): для боевого режима нужен форк с проверкой.
- `ref` роботов в каталоге — ветка или тег. Закрепление на SHA коммита сделает сборку воспроизводимой и
  защитит от подмены истории в чужом репозитории; решить до первого боевого развёртывания.
