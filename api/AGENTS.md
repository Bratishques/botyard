# AGENTS.md — botyard/api

Бэкенд Botyard: админ-API, вебхуки Dokploy, воркер саги, outbox relay, reconciler.
Устройство системы описано в `docs/architecture.md`, план — в `docs/roadmap.md`. Перед правкой домена,
саги или машины состояний прочитать оба файла. Если поведение меняется, документ правится в том же коммите.

## Раскладка

```
src/
  modules/<модуль>/
    domain/          сущности, правила, машина состояний, порты (интерфейсы). Без Nest, без SQL, без HTTP
    application/     сценарии: одно публичное действие — один метод (класс-сценарий или метод сервиса агрегата)
    infrastructure/  адаптеры портов: Postgres-репозитории, каталог Dokploy, RabbitMQ, проверки готовности
    presentation/    контроллеры, DTO, guards
  shared/            то, что нужно больше чем одному модулю: конфиг, база, шифрование, логи и метрики
  cli/               разовые команды: миграции
  main.ts            выбор процесса по PROCESS_ROLE=http|worker|relay|reconciler
migrations/          миграции Kysely (TS-файлы с SQL), только вперёд — без `down`
test/integration/    интеграционные тесты на Postgres из ../infra, база botyard_test
```

Адаптер называется по системе, с которой работает, а не по библиотеке: `PostgresDestinationRepository`,
а не `KyselyDestinationRepository` — библиотеку можно заменить, хранилище останется тем же.

Зависимости направлены внутрь: `presentation → application → domain ← infrastructure`.
Сценарий не импортирует адаптер, он получает порт через DI-токен.

## Правила кода

- TypeScript strict, без `any` и без `as` для обхода типов. Ошибка — доменный класс с кодом, а не строка.
- Параметр `unknown` типы не проверяют: в него пролезет что угодно (`Response` вместо тела). Функция, которая
  принимает `unknown` на разбор, покрывается тестом на настоящем значении — для Dokploy на записанной фикстуре.
- Комментарий объясняет «почему», а не «что». У сценария и адаптера — шапка с назначением и инвариантами.
- Каждая внешняя интеграция (Dokploy, T-Invest) идёт только через свой адаптер: таймаут, retry с jitter для
  безопасных ошибок, circuit breaker на назначение. Прямой `fetch` из сценария запрещён.
- Секреты (токены T-Invest, ключи Dokploy) хранятся только зашифрованными (`shared/crypto`: конверт, контекст через
  `secretContext(сущность, id, поле, ...привязки)` — для ключа Dokploy привязка к `base_url`). В логах, ошибках и аудите — маска: логгер маскирует поля с именами-секретами
  на любой глубине (`shared/observability/redact.ts`), но это страховка — объект с секретом целиком не логировать.
- `NODE_ENV` как признак окружения не использовать: под `bun test` Bun ставит `test`, в образе его легко
  забыть. Отличия разработки — явные флаги (`LOG_PRETTY`).
- Секрет из окружения в конфиге — `SecretValue`: значение только через `reveal()`, сериализуется маской.
- Новая таблица или колонка: миграция, тип в `src/shared/database/schema.ts` и CHECK-ограничения на
  инварианты домена в одном коммите.

## Состояние и гонки

Любая правка, которая читает и меняет состояние, перед отчётом проверяется по
[правилам гонок](.agents/rules/race-conditions.md). Коротко:

- Переход статуса — условный `UPDATE ... WHERE status = $from`, ноль строк — проигранная гонка, no-op.
- Одна активная операция на развёртывание: захват `active_operation_id IS NULL` условной записью.
- Внешний вызов — вне транзакции БД; транзакция фиксирует шаг и кладёт следующую команду в outbox.
- Таймаут или 5xx от Dokploy — неизвестный исход, а не отказ.
- Вызов Dokploy без своего ключа идемпотентности предваряется поиском по детерминированному имени.
- Повторная доставка из RabbitMQ — штатная ситуация.

## Тесты

- Доменные правила и машина состояний — unit-тесты без БД.
- Unit-тесты лежат рядом с кодом: `src/**/*.test.ts`.
- Сценарии с состоянием — интеграционные тесты в `test/integration` на настоящем Postgres из `../infra`
  (отдельная база `botyard_test`), не на моках репозиториев.
- Клиент Dokploy — контрактные тесты на записанных ответах живого инстанса (`test/fixtures/dokploy`).
- Новый баг сначала воспроизводится падающим тестом.

## Команды

Bun — единственный инструмент: рантайм, пакеты, тесты. Node.js не нужен.

```bash
docker compose -f ../infra/docker-compose.dev.yml up -d --wait   # Postgres, RabbitMQ, Redis
cp .env.example .env
bun install
bun run dev          # api с перезапуском на правки
bun run check        # biome + tsc + unit-тесты — перед каждым коммитом
bun run test:int     # интеграционные тесты, нужен запущенный infra
bun run format       # автоисправление стиля и порядка импортов
```

Импорты классов-провайдеров Nest — обычные, не `import type`: иначе DI теряет метаданные конструктора.
Поэтому правило `useImportType` в Biome выключено.

## Навыки

Навыки лежат в `.agents/skills` (для Claude Code — симлинк `.claude/skills`).

- Перед изменением поведения, кода или конфигурации — [botyard-prepare](.agents/skills/botyard-prepare/SKILL.md).
  Для правки документации — его шаги только к источнику и затронутому разделу.
- Перед отчётом об изменениях — [botyard-verify](.agents/skills/botyard-verify/SKILL.md): проверки и два
  независимых ревью, для состояния и саги — третий проход только на гонки. Для объяснения без правок ревью
  не нужно.
- При подтверждённой ошибке агента — [botyard-error-learning](.agents/skills/botyard-error-learning/SKILL.md):
  исправить, обновить конкретное правило, записать урок в
  [реестр](.agents/knowledge/lessons/agent-errors.md). Перед похожей задачей читать в реестре релевантные темы.
- При изменении админ-API — обновить [контракт](docs/api-contract.md) и его журнал.

## Git и завершение задачи

1. Перед первой правкой проверить `git status --short --branch`. Чужие незакоммиченные изменения не трогать,
   не сбрасывать и не включать в задачу.
2. До публикации на GitHub работа идёт в `main`. После публикации — ветка от свежего `main` на задачу и PR.
3. Один логический шаг — один коммит, сообщение на английском в повелительном наклонении. В коммит —
   только задача. Без трейлеров соавторства и подписей генератора.
4. Перед отчётом — проверки и ревью по botyard-verify. Найденное исправить и проверить повторно.
5. Отчёт в чате: что изменилось, новые ENV, проверки с фактическим результатом, гонки, ограничения.
6. Коммит — по разрешению владельца; в рамках выданного разрешения не переспрашивать.
   Push и публикация на GitHub — только по отдельной явной просьбе.
