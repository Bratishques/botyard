# Проверка результата

Соблюдать [AGENTS.md](../../../AGENTS.md). Глубина проверки соответствует задаче: для правки текста —
смысл, ссылки и отсутствие противоречий; для поведения — фактический путь выполнения и стыки.

Сначала определить наблюдаемый критерий результата по требованиям и проверять по нему, а не подгонять
критерий под написанный код. Недоступная существенная проверка остаётся названным ограничением.

## 1. Проверки

- `bun run check` (Biome, tsc, unit-тесты) — для любой правки кода. Коммит зависит от результата: `check && test:int && git commit`,
  а не через `;` — упавшая проверка останавливает коммит. Для сценариев с состоянием —
  `bun run test:int` на базе `botyard_test`. Отказ `beforeAll`, подключения или импорта означает, что
  проверяемый путь не выполнялся, а не что тесты зелёные.
- Тест с моками не доказывает регистрацию, вызов и совместимость с настоящим хранилищем. Для интеграционной
  правки проверить стыки: модуль Nest подключён, миграция применяется и повторно ничего не делает, формат
  записи совпадает с чтением, адаптер Dokploy разбирает записанный ответ.
- Для HTTP проверить запуском: `bun src/main.ts` и запрос к ручке, включая отказной случай.
- Проверку самого теста делать обратимой мутацией: снять проверяемую строку кода, прогнать тест, увидеть
  падение **нужного** утверждения с ожидаемым расхождением, вернуть строку тем же способом, подтвердить зелёный
  прогон. Файлы с незакоммиченной работой не восстанавливать из git (`checkout`, `restore`, `stash`).
- Сверить каждый фрагмент diff с требованием и образцами. Удалить расширение задачи без основания. Отдельно
  проверить новые объявления, обход общих механизмов (прямой `fetch`, SQL мимо репозитория, секрет мимо
  шифрования) и изменение формата хранимого состояния.
- При изменении админ-API обновить [контракт](../../../docs/api-contract.md) для `admin` в той же правке.

## 2. Гонки

Для правки, которая читает и меняет состояние (БД, RabbitMQ, статусы, операции, секреты, вызовы Dokploy),
применить [правила гонок](../../rules/race-conditions.md) и провести отдельный проход ревью только на гонки.

## 3. Два независимых ревью

Ревью проводится субагентами без общего контекста с автором. Каждому передать: исходный запрос и уточнения,
точный диапазон diff (`git diff <base>..HEAD` или рабочее дерево), источники требований, найденный путь
выполнения, образцы и фактические результаты проверок. Свои выводы автора как готовый ответ не передавать:
ревьюер читает первоисточники сам. Ревьюеры не меняют файлы и не запускают других ревьюеров.

- **Первый — требования и архитектура:** точный объём, существующий путь и его регистрация, инварианты из
  `docs/architecture.md`, отсутствие параллельного механизма, наблюдаемый результат реализован.
- **Второй — соглашения и совместимость:** слой и ответственность кода, чтение и запись состояния, миграции
  и типы схемы, форматы данных и ENV, соответствие образцам, обращение с секретами, достаточность проверок
  на стыках.
- **Третий, для состояния и саги — только гонки:** список изменяемых значений и конфликтующих операций
  передать явно.

Каждый ревьюер сообщает, что фактически проверил и что осталось недоступным. Находки исправить и передать
на повторную проверку. Ошибочное замечание закрыть проверяемым обоснованием. Отсутствие замечаний при
непрочитанном пути не означает завершённую проверку.

Если в задаче была подтверждённая ошибка агента, до отчёта выполнить [анализ ошибки](../botyard-error-learning/SKILL.md).

## 4. Публикация

Текст для публикации (описание PR, комментарий, релиз) пишется в файл с уникальным для задачи именем —
временная папка общая с другими агентами, общее имя (`pr-body.md`) может оказаться чужим. Если команда,
записывающая файл, не выполнилась, файл не считается своим. Перед отправкой — сверить содержимое с задачей,
после — перечитать опубликованное с GitHub.

## 5. Отчёт

Коротко: что изменилось, новые ENV (имя, назначение, обязательность, умолчание — без значений секретов),
выполненные проверки с фактическим результатом, разобранные и оставшиеся гонки, ограничения. Различать
проверку кода, проверку на живом Dokploy и работающий стенд. Известное незакрытое требование не позволяет
объявить задачу готовой.

**Готово:** согласованный результат реализован, стыки проверены, ревью закрыты, непроверенное названо.
