# AGENTS.md — botyard/admin

Админка операторов Botyard: назначения, клиенты, каталог, развёртывания; логи и аудит — когда API их отдаст.
Работает только с админ-API из `../api`; контракт — `../api/docs/api-contract.md`, устройство — `../api/docs/architecture.md`.

## Стек

Bun (пакеты, скрипты, тесты), React 19, Vite, TypeScript strict, TanStack Router (маршруты в коде, `src/router.tsx`)
и Query, формы — react-hook-form + zod (`@hookform/resolvers/zod`), стили — Tailwind CSS v4 через плагин Vite.
Пакет `@botyard/admin` в workspaces монорепо; устройство и запуск — `README.md`.

## Правила

- Админка не хранит секретов: токен T-Invest и API-ключ Dokploy уходят в API один раз при сохранении и
  обратно приходят только маской.
- Секреты не попадают ни в `localStorage`/`sessionStorage`, ни в кеш запросов: поле ключа или токена живёт только
  в открытой форме. Мутации TanStack держат тело в `variables`, поэтому у них `gcTime: 0` (`main.tsx`): после
  закрытия формы тело с секретом из кеша уходит. Сессия — HttpOnly-cookie, JS её не видит.
- API — только с того же origin под префиксом `/api` (прокси Vite, в проде — обратный прокси): иначе не работают
  cookie `SameSite=Strict` и защита от CSRF. CORS в api не открывать.
- Схемы тел и view-типы ответов — из `@botyard/contract`, не переопределять в админке. Форма может сузить схему
  (непустое имя), но не ослабить.
- Каждое изменяющее действие над развёртыванием отправляет `Idempotency-Key` (UUID на попытку пользователя, а не на
  HTTP-запрос): повтор после обрыва не создаёт вторую операцию. Попытка = открытая форма или диалог (`useAttempt`):
  ключ рождается при открытии, переживает ошибки и повторы и меняется только после подтверждённого успеха. Тело
  (`version`) фиксируется при открытии диалога. Ключ не привязан к телу: правка данных после попытки, которая могла
  пройти, получит `409 IDEMPOTENCY_CONFLICT` — так и задумано.
- Назначения и клиенты ключа не получают (их защищают уникальность и `version`), но диалог правки тоже фиксирует
  `version`, которую видел оператор: чужая правка даёт конфликт, а не перезапись.
- Статус развёртывания пока приходит опросом (`src/api/live.ts`: раз в 3 с, пока есть активная операция); SSE этапа 3
  подключается там же, экраны об источнике обновлений не знают. Оптимистичных переходов статуса нет: показывается
  то, что подтвердил сервер (в том числе ответ на действие — принятая операция).
- Включение боевого режима (`sandbox = false`) — отдельное подтверждение с вводом имени клиента.
- Ошибка API показывается по коду (`OPERATION_IN_PROGRESS`, `DESTINATION_UNREACHABLE`), а не сырым текстом
  (`src/api/errors.ts`; неизвестный код показывается сам). `message` из ответа в интерфейс не попадает даже для
  `VALIDATION_FAILED` и `DEPLOYMENT_INVALID_CONFIG`. Поля состояния без кода — `lastError` назначения и развёртывания,
  `error` операции — показываются как есть: это записанная сервером причина без секретов, а не текст ошибки запроса.
- Форма конфига строится по JSON Schema шаблона (`src/schema-form`): object, array (в том числе объектов), string,
  enum, number, integer, boolean, `default`, `required`; остальное — поле JSON. Проверка формы — подсказка, источник
  истины — сервер. Необязательные объект и массив без ввода в конфиг не попадают. Обязательные поля идут первыми: API хранит схему в jsonb, и порядок ключей теряется.
