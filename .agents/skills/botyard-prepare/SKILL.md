# Подготовка изменения

Соблюдать [AGENTS.md](../../../AGENTS.md) репозитория и [общие правила рабочей области](../../../../AGENTS.md).
Глубина подготовки соответствует задаче: для правки текста достаточно источника и связанного раздела, для
изменения поведения нужны фактический путь выполнения и затронутые стыки.

Технические решения принимать самостоятельно по проекту и [архитектуре](../../../docs/architecture.md).
Если после исследования остаётся выбор поведения для оператора или клиента, уточнить его с конкретной
рекомендацией. Перед существенной реализацией коротко сообщить понимание задачи и продолжать без ожидания
подтверждения, если существенной неоднозначности нет.

## 1. Установить объём

Проверить релевантные темы [реестра ошибок](../../knowledge/lessons/agent-errors.md). Всю историю заранее не загружать.

- Собрать из диалога результат, ограничения, исключения и критерии приёмки. Последующие уточнения включать
  в ту же сводку, прежние требования без отмены пользователем сохранять.
- Каждый пункт реализации должен следовать из требования, [плана](../../../docs/roadmap.md) или
  отдельного указания. Соседнее улучшение — отдельно названное предложение, а не часть правки.
- Для наборов (статусы, шаги саги, способы доставки конфига, роли процесса) выписать точный состав
  и исключённые элементы. Возможность Dokploy или робота не доказывает, что она входит в задачу.

**Готово:** известен проверяемый результат, каждому изменению соответствует требование.

## 2. Найти существующий путь выполнения

- От точки входа (контроллер, сообщение очереди, вебхук, расписание reconciler) проследить вызовы до
  изменения данных и до потребителя результата. Прочитать реализации на пути и регистрацию в модулях Nest;
  поиск по названию и один похожий файл недостаточны.
- Найти существующие общие механизмы по ответственности: unit of work, outbox, адаптер Dokploy, шифрование,
  аудит, машина состояний. Расширять их; новый механизм обосновывать конкретной недостающей возможностью.
- Для фонового поведения проверить производителя, outbox, relay, очередь RabbitMQ, обработчик шага, запись
  результата и следующую команду.
- Для кода найти 2–3 образца с той же ролью и сверить размещение по слоям, способ доступа к данным и обработку
  ошибок. Расхождение образца с явным правилом разобрать, а не размножать.
- Перед созданием файла из shell проверить, что пути нет (`test -e`): `cat >` и `tee` молча перезаписывают.

**Готово:** названы конкретные файлы пути, точка расширения и образцы.

## 3. Договорённости о данных и внешних системах

- Для каждого затронутого значения определить владельца, источник истины, писателя, читателей и жизненный цикл.
  Различать секрет (токен T-Invest, ключ Dokploy), конфигурацию запуска (ENV), состояние (БД) и производный кеш.
- Для БД прочитать миграции и `src/shared/database/schema.ts`: ограничения, уникальные индексы, триггеры.
  Новая таблица или колонка — миграция и тип в одном коммите.
- Для Dokploy сверять метод и тело запроса с OpenAPI текущей версии, а форму ответа — с фикстурами в
  `test/fixtures/dokploy`. Ответы в OpenAPI не описаны: догадка о поле ответа без фикстуры — непроверенное
  предположение, так и обозначить.
- **Ответы Dokploy содержат секреты**: `application.one` возвращает env приложения с токеном клиента.
  Сырой ответ не печатать и не логировать. Неизвестную структуру изучать по именам ключей, значения
  выводить только явным списком скалярных полей.
- Для роботов факты (переменные, пути, порты) проверять по upstream-репозиторию со ссылкой на файл.
- Версии зависимостей новее памяти модели: API библиотеки проверять по установленному пакету
  (`node_modules/<pkg>/package.json`, `exports`, `.d.ts`), а не по воспоминанию.

**Готово:** известны договорённости о данных и способ проверить совместимость.

До первой правки дать короткое сообщение: что входит в задачу, какой путь расширяется, какие соглашения
сохраняются и чем будет проверен результат.
