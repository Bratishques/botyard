# Botyard — архитектура

Botyard разворачивает торговых роботов T-Invest API (Т-Банк Инвестиции) для клиентов на серверах под
управлением [Dokploy](https://dokploy.com). Оператор в админке заводит назначения (Dokploy-инстансы),
клиентов с их токенами T-Invest и выбирает шаблон робота. Остальное делает платформа: создаёт приложение
в Dokploy, собирает образ из исходников робота, передаёт конфиг и секреты, запускает, следит
за состоянием и отдаёт логи.

Роботы — сторонние open-source проекты (см. репозиторий `bots`). Платформа их не меняет: она
оркестрирует развёртывание. По умолчанию роботы работают только в **песочнице** T-Invest.

## Компоненты

```
 ┌────────────┐  HTTPS   ┌──────────────────────── api (NestJS) ─────────────────────────┐
 │ admin (SPA)│ ───────► │ HTTP: админ-API, вебхуки Dokploy, SSE логов                   │
 └────────────┘          │                                                               │
                         │ Postgres ◄── сценарии пишут состояние + outbox одной транзакцией│
                         │    │                                                          │
                         │    └─► outbox relay ──► RabbitMQ ──► worker (шаги саги)       │
                         │                                         │                     │
                         │ reconciler (по расписанию): сверка с Dokploy, зависшие саги    │
                         └─────────────────────────────────────────┼─────────────────────┘
                                                                   │ x-api-key, у каждого назначения свой
                                   ┌───────────────────────────────▼──────────────┐
                                   │ Dokploy (назначение)                         │
                                   │  git clone робота → docker build → Swarm     │
                                   │  контейнер робота ──gRPC──► T-Invest API     │
                                   └──────────────────────────────────────────────┘
```

- **api** — один кодовый репозиторий, несколько процессов: `http`, `worker`, `relay`, `reconciler`. Каждый
  процесс stateless, реплик может быть несколько.
- **Postgres** — источник истины: назначения, клиенты, развёртывания, журнал операций, outbox, inbox
  вебхуков, аудит.
- **RabbitMQ** — доставка команд саги воркерам. Доставка «хотя бы один раз», поэтому каждый шаг идемпотентен.
- **Dokploy** — исполнитель. Его API не идемпотентен и не типизирован в ответах (OpenAPI описывает только
  запросы), поэтому весь доступ идёт через один адаптер с контрактными тестами.

## Домен

| Сущность | Смысл | Ключевые поля |
|---|---|---|
| `Destination` | Куда разворачивать: Dokploy-инстанс и, по желанию, удалённый сервер в нём | `baseUrl` (нормализован), `apiKey` (зашифрован, наружу — `apiKeyHint`), `projectId`, `environmentId`, `serverId?`, `status`: `ACTIVE` / `UNREACHABLE` (последняя проверка не прошла) / `DISABLED` (выключено оператором, новые развёртывания не принимает), `version` |
| `Customer` | Для кого разворачивается робот | `name`, `tinvestToken` (зашифрован), `accountId`, `sandbox` |
| `BotTemplate` | Описание робота из репозитория `bots` | `gitUrl`, `ref`, `dockerfile`, `context`, `configSchema`, способ передачи конфига (`env` / `file`) |
| `BotDeployment` | Робот конкретного клиента на конкретном назначении | `status`, `config`, `dokployAppId?`, `appName` (детерминирован), `activeOperationId?` |
| `Operation` | Одна операция над развёртыванием: provision, start, stop, redeploy, delete | `kind`, `status`, `step`, `attempt`, `idempotencyKey`, `error?` |
| `OutboxMessage` | Команда или событие, записанное в одной транзакции с состоянием | `topic`, `payload`, `publishedAt?` |
| `InboxMessage` | Принятый вебхук Dokploy, дедупликация | `dedupKey` (уникален), `receivedAt` |
| `AuditEvent` | Кто, что и когда сделал в админке. Только дописывание: UPDATE, DELETE и TRUNCATE запрещены триггером | `actor`, `action`, `targetType`, `targetId`, `payload` (объект), `createdAt` (ставит база) |

`appName` в Dokploy выводится из id развёртывания (`by-<первые 12 символов id>`). Это естественный ключ
идемпотентности для API, у которого своего ключа нет (см. сагу).

## Машина состояний развёртывания

```
            provision                 deploy ok
 DRAFT ─────────────► PROVISIONING ───────────► RUNNING ◄──────┐
                          │                       │  stop      │ start
                          │ ошибка                ▼            │
                          ▼                   STOPPED ─────────┘
                        FAILED ── retry ──► PROVISIONING
   любое, кроме DELETED ── delete ──► DELETING ──► DELETED (терминально)
```

- Переход — только условный `UPDATE ... WHERE id = $1 AND status = $from`. Проигравший получает 0 строк
  и ничего не делает.
- В каждый момент у развёртывания не больше одной активной операции: её захватывает условная запись
  `activeOperationId IS NULL`. Вторая команда («стоп» во время провижининга) получает `409 OPERATION_IN_PROGRESS`,
  `delete` встаёт в очередь за текущей операцией.

## Сага развёртывания (provision)

Оркестрация: шаги и переходы задаёт один сценарий, воркер выполняет по одному шагу на сообщение.

| # | Шаг | Вызов Dokploy | Как сделан идемпотентным | Компенсация |
|---|---|---|---|---|
| 1 | Найти или создать приложение | `GET application.search?appName=` → `POST application.create` | Сначала поиск по детерминированному `appName`: если ответ на прошлый `create` потерялся, приложение найдётся, а не создастся второе | `application.delete` |
| 2 | Источник | `application.saveGitProvider` | Перезапись тем же значением | — |
| 3 | Сборка | `application.saveBuildType` (`dockerfile`) | Перезапись | — |
| 4 | Конфиг и секреты | `application.saveEnvironment` или `mounts.create` | env — перезапись; mount — поиск существующего по `mountPath` перед созданием | — |
| 5 | Деплой | `application.deploy` | Перед повтором проверяется последний деплой в `deployment.all`; новый не запускается, пока идёт прошлый | — |
| 6 | Дождаться исхода | вебхук `notification.createCustom` + опрос `application.one` | Вебхук и опрос ведут в один сценарий, переход условный | — |

Правила:
- **Неизвестный исход ≠ отказ.** Таймаут или 5xx на шаге — повтор с экспонентой и jitter. Компенсация только
  при определённом отказе (4xx валидации, исчерпаны попытки) — и тогда развёртывание `FAILED`, а созданное
  в Dokploy удаляется только явной операцией `delete`. Так оператор видит логи упавшей сборки.
- **Внешние вызовы — вне транзакции БД.** Транзакция фиксирует «шаг N выполнен» и кладёт в outbox команду
  шага N+1.
- **Шаг 6 не держит воркер.** Ожидание — это состояние в БД. Его закрывает вебхук, а если вебхук потерялся,
  то reconciler.

## Reconciler

По расписанию, по каждому назначению:
- операции, которые висят на шаге дольше порога, переотправляются в очередь;
- развёртывания `RUNNING` сверяются с `application.one`. Если приложение остановили или удалили руками
  в Dokploy, это фиксируется как дрейф и показывается в админке, а не «чинится» молча;
- outbox, который relay не опубликовал (relay упал), публикуется повторно.

## Гонки, которые разбираются явно

| Сценарий | Защита |
|---|---|
| Двойной клик «Развернуть» | `Idempotency-Key` от админки + `UNIQUE (customer_id, idempotency_key)`; повтор возвращает ту же операцию |
| «Стоп» во время провижининга | Захват `activeOperationId` условной записью; вторая операция получает 409 |
| Вебхук и опрос пришли одновременно | Условный переход `WHERE status = $from`; проигравший — no-op |
| RabbitMQ доставил шаг дважды | Шаг проверяет `operation.step` и `attempt` условной записью до вызова Dokploy |
| Потерян ответ на `application.create` | Поиск по `appName` перед созданием |
| Ротация API-ключа назначения во время операции | Ключ читается на каждом шаге, а не кешируется на всю сагу |
| Ротация токена клиента | Новый токен → операция `redeploy` у всех его развёртываний; старый токен из env Dokploy перезаписывается |
| `delete` против идущего деплоя | `delete` ждёт завершения активной операции; `application.cancelDeployment`, если сборка идёт |

Каждый пункт покрыт тестом с принудительным переплетением (`Promise.all` и барьеры в адаптере-заглушке).

## Безопасность

- Токены T-Invest и API-ключи Dokploy хранятся с envelope encryption: AES-256-GCM, ключ данных на запись,
  мастер-ключ из окружения. В логах и аудите — только маска.
- **Известный компромисс:** Dokploy хранит переменные окружения и содержимое file mount у себя открытым
  текстом. Назначение должно быть доверенным, это написано в README и в форме добавления назначения.
- Песочница по умолчанию. Боевой режим (`sandbox = false`) — отдельный флаг клиента, его включение
  требует подтверждения и пишется в аудит.
- API-ключ Dokploy даёт полный доступ к инстансу, поэтому у каждого назначения он свой, и проверка
  ключа (`project.all`) делается при добавлении.

## Технологии

| Часть | Выбор | Почему |
|---|---|---|
| Среда выполнения | Bun — везде: api, админка, скрипты, CI | Один инструмент: рантайм, пакеты, тесты |
| API | NestJS 12, TypeScript strict | Модули и DI под гексагональную раскладку |
| БД | PostgreSQL 17, Kysely + миграции на SQL | Явный SQL для условных записей, типы без ORM-магии |
| Очередь | RabbitMQ 4, transactional outbox | Брокер и outbox — предмет демонстрации |
| Кеш, pub/sub логов | Redis 7 | Раздача логов SSE между репликами `http` |
| Тесты | `bun test`; интеграционные — на Postgres и RabbitMQ из `infra`, отдельная тестовая БД; заглушка Dokploy на `Bun.serve` | Интеграционные тесты на настоящих зависимостях, без моков репозиториев |
| Линтер и формат | Biome | Одна утилита вместо ESLint и Prettier |
| Админка | React 19, Vite, TanStack Query и Router | SPA без SSR, нужна только операторам |
| Наблюдаемость | pino (JSON), Prometheus `/metrics`, `/health/live` и `/health/ready` | — |

## Открытые вопросы

- Ответы Dokploy в OpenAPI не описаны: схемы ответов фиксируются на живом инстансе в контрактных тестах.
- Роботы в `bots` написаны в 2022 году (Go 1.18). Сборку проверить на первом этапе; при поломке — форк
  с минимальной правкой и ссылкой на оригинал.
- Адрес API у BITA захардкожен (`invest-public-api.tinkoff.ru:443`). На 2026-11-24 домен резолвится,
  но если его отключат, BITA потребует форк. У второго робота адрес задаётся конфигом.
